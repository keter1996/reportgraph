# 安装与接入说明

## 1. 目标

本文档面向两类使用方式：

- 作为本地可安装的报表图谱服务系统，用于初始化、更新、查询、删除和监听 Report Graph 产物。
- 作为 `Codex` / `CloudCode` 可接入的稳定能力边界，通过统一命令和基于官方 .NET `ModelContextProtocol` SDK 的 MCP stdio 服务模式进行消费。

当前交付目标不是只交一个库，也不是只交一个 MCP，而是交付一整套可安装、可运行、可查询、可接入的服务系统。这个系统当前包括：

- 图谱构建能力
- 图谱存储能力
- 图谱查询能力
- 统一 CLI 命令入口
- 安装脚本与发布脚本
- 机器可读安装描述
- 宿主接入边界说明

## 2. 当前交付形态

当前仓库同时提供三种交付形态，三者共用同一套命令：

1. 客户机器、受限环境、`Codex` / `CloudCode` 自动安装：优先使用自包含发布形态。
2. 内部开发或明确具备 `.NET SDK` 的机器：可以使用源码开发形态。
3. 明确具备 `.NET SDK` 与 `dotnet tool` 能力的机器：可以使用 `.NET tool` 形态。

也就是说，不能假设客户环境一定已经具备 `.NET tool`。当前更稳妥的自动安装基线是：从 Git 地址拉取仓库后执行 `scripts\publish-reportgraph.ps1`，再调用 `artifacts\publish\win-x64\reportgraph.exe`。

### 2.1 源码开发形态

```powershell
git clone <git-url> ReportGraph
cd ReportGraph
dotnet build ReportGraph.slnx
dotnet run --project src/ReportGraph.Cli -- --help
```

### 2.2 `.NET tool` 形态

```powershell
.\scripts\install-reportgraph.ps1
```

安装完成后，工具位于：

```text
artifacts\tool\reportgraph.exe
```

### 2.3 自包含发布形态

```powershell
.\scripts\publish-reportgraph.ps1
```

发布完成后，可直接使用：

```text
artifacts\publish\win-x64\reportgraph.exe
```

这是当前面向客户环境，以及面向 `Codex` / `CloudCode` 自动安装场景的推荐交付形态。

当前对外推荐且应长期保持稳定的命令集如下：

- `init`
- `doctor`
- `update`
- `delete`
- `status`
- `mark-dirty`

无论是源码形态、`.NET tool` 形态，还是自包含发布形态，都应暴露这一套命令，不再分别设计多套入口语义。

## 5. 推荐使用方式

如果已经进入某个 PBIP 项目目录，推荐直接使用：

```powershell
reportgraph init
reportgraph doctor
reportgraph status
reportgraph mark-dirty --reason "Changed outside ReportGraph"
reportgraph query page Page1
reportgraph watch
reportgraph mcp
reportgraph update
reportgraph delete
```

如果尚未安装到系统中，也可以在仓库根目录直接使用包装脚本：

```powershell
.\scripts\reportgraph.ps1 init
.\scripts\reportgraph.ps1 status
.\scripts\reportgraph.ps1 query page Page1
```

查看帮助：

```powershell
reportgraph --help
```

查看安装与接入信息：

```powershell
reportgraph install-info
```

## 6. 命令语义

- `init [project-path-or-build-input-json]`
  为当前项目或指定项目初始化 `Graph/` 产物；不传路径时默认使用当前目录。
- `update [project-path-or-build-input-json] [--force]`
  更新当前项目或指定项目的图谱；默认只在真实变化后更新，带 `--force` 时强制重建。
- `delete [project-path]`
  删除当前项目或指定项目下的 `Graph/` 产物。
- `status [project-path]`
  查看当前项目或指定项目的图谱状态、dirty 状态、stale 原因和基础摘要。
- `doctor [project-path-or-pbip-file]`
  诊断项目结构、图谱前置条件、stale 状态与源文件跟踪情况。
- `mark-dirty [project-path] [--reason <reason>]`
  仅标记当前项目或指定项目为 dirty，不立即重建。
- `query [project-path] <tool> ...`
  针对图谱执行结构化查询；若 `graph` 缺失、`manifest` 缺失、源文件指纹变化或存在 dirty 标记，则会先自动刷新。
- `watch [project-path] [--refresh] [--debounce-ms <milliseconds>]`
  监听稳定源文件集合；默认只标记 dirty，带 `--refresh` 时直接刷新。
- `mcp`
  以 stdio 方式启动 ReportGraph MCP 服务；MCP 工具调用同样会在消费前自动刷新。
- `install-info`
  输出当前系统的安装方式、接入边界和建议使用模式。

## 7. 当前支持的项目入口

当前项目入口解析顺序如下：

1. 直接传入 `report-graph.build-input.json`
2. 传入项目目录，由适配层查找 `report-graph.build-input.json`
3. 传入 `.pbip` 文件路径，由适配层回退到项目目录继续解析
4. 若未找到标准输入文件，则直接尝试解析最小 PBIP 项目结构

## 8. 当前支持的 PBIP / 模型读取范围

报表侧：

- `*.pbip`
- `*.Report/definition.pbir`
- `*.Report/definition/pages/pages.json`
- `*.Report/definition/pages/<page>/page.json`
- `*.Report/definition/pages/<page>/visuals/<visual>/visual.json`

语义模型侧：

- `*.SemanticModel/model.bim`
- `*.SemanticModel/definition/database.tmdl`
- `*.SemanticModel/definition/model.tmdl`
- `*.SemanticModel/definition/tables/*.tmdl`
- `*.SemanticModel/definition/relationships.tmdl`

Markdown 侧：

- 纳入稳定源集合的 `.md` 文件

当前不会计入真实源变化的内容包括：

- `Graph/`
- `.pbi/`
- `bin/`
- `obj/`
- `node_modules/`
- 隐藏文件

## 10. 与 Codex / CloudCode 的接入关系

目标安装方式是：

- `Codex` / `CloudCode` 通过一个 Git 地址拉取仓库
- 根据环境能力执行安装脚本或发布脚本；默认优先执行自包含发布脚本
- 通过统一 CLI 命令消费报表图谱能力
- 通过 `reportgraph mcp` 暴露结构化工具能力，而不重做底层扫描逻辑

推荐的自动安装流程如下：

```powershell
git clone <git-url> ReportGraph
cd ReportGraph
powershell -ExecutionPolicy Bypass -File .\scripts\publish-reportgraph.ps1
.\artifacts\publish\win-x64\reportgraph.exe --help
```

安装完成后，宿主应把下面这个可执行文件作为主入口：

```text
<repo-root>\artifacts\publish\win-x64\reportgraph.exe
```

如果宿主要启动 MCP，则使用同一个可执行文件：

```powershell
.\artifacts\publish\win-x64\reportgraph.exe mcp
```

如果宿主已经自行感知到外部变化，建议只调用：

```powershell
reportgraph mark-dirty <project-root> --reason "Changed outside ReportGraph"
```

然后把真正刷新延迟到下一次 `query` 或 MCP 工具调用。

推荐的宿主消费顺序如下：

1. 安装或发布 ReportGraph，并固定主入口为 `reportgraph.exe`
2. 启动 `reportgraph.exe mcp`
3. 先调用 `report.graph.status` 判断当前项目是否 dirty 或 stale
4. 若宿主已感知外部变化，则调用 `report.graph.mark_dirty`
5. 再调用 `report.page.get`、`report.measure.get`、`report.graph.explore` 等查询工具消费结果

这样宿主只负责提供上下文、通知变更和消费结果，而图谱是否需要刷新仍由 ReportGraph 自己判断。

## 11. 稳定产物与本地状态文件

当前 `Graph` 产物按“只跟随真实源变更更新”的目标收敛：

- `manifest.json` 记录源文件指纹与构建元数据
- `dirty-state.json` 记录宿主通知或 watch 标记的脏状态
- `.pbi/`、隐藏文件和本地缓存文件不会参与稳定性判断
- `query` 和 MCP 会在消费前自动把 dirty 状态清理并完成刷新

这点对 `Codex` / `CloudCode` 接入很重要。宿主可以把 `Graph/` 目录视为可缓存、可 diff、可复用的本地图谱服务产物，而不是每次启动都无意义地重建。

## 12. 当前已验证的链路

当前已经实际验证：

- `scripts\publish-reportgraph.ps1` 可生成 `artifacts\publish\win-x64\reportgraph.exe`
- `reportgraph.exe --help` 可用
- `reportgraph.exe init <pbip>` 可生成 `Graph/` 产物
- `reportgraph.exe doctor <project>` 可显示 stale 与 dirty 状态
- `reportgraph.exe status <project>` 可显示 dirty 标记与源文件跟踪信息
- `reportgraph.exe mark-dirty <project>` 可写入 dirty 状态
- `reportgraph.exe query <project> page <pageId>` 可在 dirty 或 stale 时自动刷新
- 官方 MCP Client 可通过 stdio 连接 `reportgraph.exe mcp` 并调用工具
- `report.graph.status` 与 `report.graph.mark_dirty` 已可通过 MCP 正常调用

## 13. 交付建议

推荐按环境选择交付方式：

- 开发团队本地调试：源码开发形态
- 已具备 SDK 的内部机器：`.NET tool` 形态
- 客户机器、受限机器、自动安装场景：自包含发布形态

也就是说，后续如果用户只是告诉 `Codex` “从这个 Git 地址安装 ReportGraph 并使用”，目标就是让安装动作优先走仓库脚本与机器可读描述，而不是要求用户自己打开源码手工运行。
