# 04-【报表图谱】- 安装与接入说明

## 1. 目标

本说明面向两类使用方式：

- 作为本地可安装的图谱服务系统，用于初始化、更新、查询、删除 Report Graph 产物
- 作为 `Codex` / `CloudCode` 可接入的稳定能力边界，通过统一命令和基于官方 .NET `ModelContextProtocol` SDK 的 MCP stdio 服务模式进行消费

当前交付目标不是单独交一个库，也不是只交一个 MCP，而是交付一整套可安装、可运行、可查询、可接入的服务系统。这个系统当前包含：

- 图谱构建能力
- 图谱存储能力
- 图谱查询能力
- 统一 CLI 命令入口
- 安装脚本与发布脚本
- 机器可读安装描述
- 宿主接入边界说明

## 2. 当前交付形态

当前仓库已经同时提供三种交付形态，三者共用同一套命令：

默认推荐顺序如下：

1. 客户机器、受限机器、`Codex` / `CloudCode` 自动安装：优先使用自包含发布形态
2. 内部开发或明确具备 `.NET SDK` 的机器：可以使用源码开发形态
3. 明确具备 `.NET SDK` 与 `dotnet tool` 能力的机器：可以使用 `.NET tool` 形态

也就是说，不能假设客户环境一定已经具备 `.NET tool`。当前更稳妥的自动安装基线是：从 Git 地址拉取仓库后执行 `scripts\publish-reportgraph.ps1`，再调用 `artifacts\publish\win-x64\reportgraph.exe`。

### 2.1 源码开发形态

适合开发、调试、继续扩展功能。

```powershell
git clone <git-url> ReportGraph
cd ReportGraph
dotnet build ReportGraph.slnx
dotnet run --project src/ReportGraph.Cli -- --help
```

### 2.2 `.NET tool` 形态

适合本机已经具备 `.NET SDK` 与 `dotnet tool` 能力的环境。

```powershell
.\scripts\install-reportgraph.ps1
```

安装完成后，工具位于：

```text
artifacts\tool\reportgraph.exe
```

### 2.3 自包含发布形态

适合客户机器不方便依赖 `.NET SDK`、`dotnet tool` 或不希望手工打开源码运行的场景。

```powershell
.\scripts\publish-reportgraph.ps1
```

发布完成后，可直接使用：

```text
artifacts\publish\win-x64\reportgraph.exe
```

这是当前面向客户环境、以及面向 `Codex` / `CloudCode` 自动安装场景的推荐交付形态。

## 4. 统一命令集

当前对外推荐且应长期保持稳定的命令集如下：

- `init`
- `update`
- `delete`
- `status`
- `query`
- `mcp`
- `install-info`

无论是源码形态、`.NET tool` 形态，还是自包含发布形态，都应暴露这一套命令，不再分别设计多套入口语义。

## 5. 推荐使用方式

如果已经进入某个 PBIP 项目目录，推荐直接使用：

```powershell
reportgraph init
reportgraph status
reportgraph query page Page1
reportgraph mcp
reportgraph update
reportgraph delete
```

如果尚未安装到系统中，也可以在仓库根目录直接使用包装脚本：

```powershell
.\scripts\reportgraph.ps1 init
.\scripts\reportgraph.ps1 status
.\scripts\reportgraph.ps1 query page Page1
```

查看帮助：

```powershell
reportgraph --help
```

查看安装与接入说明：

```powershell
reportgraph install-info
```

## 6. 命令语义

- `init [project-path-or-build-input-json]`
  为当前项目或指定项目初始化 `Graph/` 产物；不传路径时默认使用当前目录。
- `update [project-path-or-build-input-json] [--force]`
  更新当前项目或指定项目的图谱；默认只在真实变更后更新，带 `--force` 时强制重建。
- `delete [project-path]`
  删除当前项目或指定项目下的 `Graph/` 产物。
- `status [project-path]`
  查看当前项目或指定项目的图谱状态、产物存在情况与基础摘要。
- `query [project-path] <tool> ...`
  针对已落盘图谱执行结构化查询；如果当前已经位于项目目录中，可省略项目路径。
- `mcp`
  以 stdio 方式启动 ReportGraph MCP 服务，供 `Codex`、`CloudCode` 或其他支持 MCP 的宿主直接连接。
- `install-info`
  输出当前系统的安装方式、接入边界和建议使用模式。

## 7. 当前支持的项目入口

当前项目入口解析顺序如下：

1. 直接传入 `report-graph.build-input.json`
2. 传入项目目录，由适配层查找 `report-graph.build-input.json`
3. 传入 `.pbip` 文件路径，由适配层回退到项目目录继续解析
4. 传入 `.pbix` 文件路径时，先进入托管转换边界：
   - 若同目录已存在可解析的 PBIP 项目，则直接复用
   - 若不存在可复用 PBIP，则提示用户通过 Power BI Desktop 另存为 PBIP
5. 若未找到标准输入文件，则直接尝试解析最小 PBIP 项目结构

## 8. 当前已支持的 PBIP / 模型读取范围

报表侧：

- `*.pbip`
- `*.pbix` 入口
- `*.Report/definition.pbir`
- `*.Report/definition/pages/pages.json`
- `*.Report/definition/pages/<page>/page.json`
- `*.Report/definition/pages/<page>/visuals/<visual>/visual.json`

语义模型侧：

- `*.SemanticModel/model.bim`
- `*.SemanticModel/definition/database.tmdl`
- `*.SemanticModel/definition/model.tmdl`
- `*.SemanticModel/definition/tables/*.tmdl`
- `*.SemanticModel/definition/relationships.tmdl`

当前 TMDL 解析已覆盖最小建图对象：

- 模型名
- 表
- 列
- 度量值
- 关系

当前暂未支持：

- PBIR-Legacy `report.json`
- 更复杂的视觉对象查询表达式
- 更完整的 TMDL 语法覆盖

### 8.1 当前 PBIX 托管转换策略

当前 `PBIX` 不直接进入核心解析器，而是通过托管转换进入标准 `PBIP` 链路：

- 优先复用同目录已存在的 PBIP 项目
- 若不存在可复用 PBIP，则由用户通过 Power BI Desktop 执行“另存为 Power BI Project (PBIP)”
- 转换完成后，适配层会继续读取 `.pbip` 或 `*.Report + *.SemanticModel` 结构并建图

如果未找到可复用 PBIP，CLI 会明确提示先通过 Power BI Desktop 另存为 PBIP。

## 9. 当前查询能力

当前 `query` 已支持：

- `graph`
- `page <pageId>`
- `page-bindings <pageId>`
- `table <tableName>`
- `visual <pageId> <visualId>`
- `explore <from-page|from-table> <identifier>`

示例：

```powershell
reportgraph init D:\Example\SalesProject
reportgraph status D:\Example\SalesProject
reportgraph query D:\Example\SalesProject page Page1
reportgraph update D:\Example\SalesProject --force
reportgraph delete D:\Example\SalesProject
```

## 10. 与 Codex / CloudCode 的接入关系

目标安装方式是：

- `Codex` / `CloudCode` 通过一个 Git 地址拉取仓库
- 根据环境能力执行安装脚本或发布脚本；默认优先执行自包含发布脚本
- 通过统一 CLI 命令消费图谱服务能力
- 通过 `reportgraph mcp` 暴露结构化工具能力，不重做底层扫描逻辑

推荐的自动安装流程如下：

```powershell
git clone <git-url> ReportGraph
cd ReportGraph
powershell -ExecutionPolicy Bypass -File .\scripts\publish-reportgraph.ps1
.\artifacts\publish\win-x64\reportgraph.exe --help
```

安装完成后，宿主应把下面这个可执行文件作为主入口：

```text
<repo-root>\artifacts\publish\win-x64\reportgraph.exe
```

如果宿主要启动 MCP，则使用同一个可执行文件：

```powershell
.\artifacts\publish\win-x64\reportgraph.exe mcp
```

当前仓库提供 `codex-install.json` 作为机器可读安装描述，表达的也是这条优先路径：

- 安装步骤：`powershell -ExecutionPolicy Bypass -File .\scripts\publish-reportgraph.ps1`
- 主命令：`.\artifacts\publish\win-x64\reportgraph.exe`
- 示例命令：`init`、`status`、`query`

当前已经具备的基础条件：

- 图谱构建、存储、查询能力已拆分成独立模块
- 分发层已统一描述 CLI / MCP / 安装边界
- CLI 已具备可执行的 `init / update / delete / status / query / mcp`
- 已提供 `.NET tool` 安装路径
- 已提供自包含发布路径
- 已提供 `codex-install.json` 作为机器可读安装描述起点
- Markdown 输出作为一等产物保留，适合对 `md` 友好的存储与消费链路

当前已落地的 MCP 工具包括：

- `report.graph.load`
- `report.page.get`
- `report.page.bindings`
- `report.model.table.get`
- `report.visual.get`
- `report.graph.explore`

MCP 运行时由官方 .NET `ModelContextProtocol` SDK 承载，宿主侧可以按标准 MCP stdio 方式启动：

```powershell
reportgraph mcp
```

当前测试已使用官方 `ModelContextProtocol.Client.McpClient` 与 `StdioClientTransport` 真实连接该入口，验证 `tools/list` 与 `tools/call` 可用。

## 11. 稳定输出与本地状态文件

当前 `Graph` 产物已按“只跟随真实源变更更新”的目标收敛：

- `generatedAtUtc` 基于真实源工件的最后修改时间推导
- `.pbi/`、隐藏文件、本地缓存文件、编辑器本地状态文件不会参与时间戳计算
- 连续 `update --force` 同一份 PBIP 时，`Graph\report-graph.json` 与 `Graph\manifest.json` 应保持稳定

这点对 `Codex` / `CloudCode` 接入很重要。宿主可以放心把 `Graph/` 目录当作可缓存、可 diff、可复用的本地服务产物，而不是每次启动都无意义刷新。

## 12. 当前已验证的链路

当前已经实际验证：

- `scripts\publish-reportgraph.ps1` 可生成 `artifacts\publish\win-x64\reportgraph.exe`
- 发布版 `reportgraph.exe --help` 可用
- 发布版 `reportgraph.exe init <pbip>` 可生成 `Graph/` 产物
- 发布版 `reportgraph.exe status <project>` 可读取图谱状态
- 发布版 `reportgraph.exe query <project> page <pageId>` 可查询页面
- 官方 MCP Client 可通过 stdio 连接 `reportgraph.exe mcp` 并调用工具
- 样例 PBIP 连续两次 `update --force` 后，`report-graph.json`、`manifest.json` 与 `generatedAtUtc` 保持一致

## 13. 交付建议

推荐按环境选择交付方式：

- 开发团队本地调试：源码开发形态
- 已具备 SDK 的内部机器：`.NET tool` 形态
- 客户机器、受限机器、自动安装场景：自包含发布形态

也就是说，后续如果用户只是告诉 `Codex` “从这个 Git 地址安装 ReportGraph 并使用”，目标就是让安装动作优先走仓库脚本与机器可读描述，而不是要求用户自己打开源码手工运行。
